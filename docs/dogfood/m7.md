# M7 dogfood: GPU client, sandbox and tooling

## m07-base captures on the GPU client: no core hardware adapter (cards 4462..4486), 2026-10-23

What broke:
- The programmatic card ran `bash scripts/build-lookdev.sh` (exit 0), then
  `node scripts/lookdev-capture.mjs --milestone m07` (exit 1). All 7 m07-base variants (agx,
  aces, exposure-up, msaa-on, msaa-off, vertex-colors, empty) rendered without GPU errors,
  nonEmpty true, passes `prepass > forward > tonemap`. But every one ran on adapter
  `SwiftShader Device (Subzero)`, which is **software**. So the script correctly failed each
  pair with "captured on a software adapter" (Q13 needs hardware true).
- Cause: the GPU client's Chrome (WSL) has no core WebGPU adapter on the RTX 3090. Its only
  hardware adapter is `ANGLE (Microsoft Corporation, D3D12 (NVIDIA GeForce RTX 3090), OpenGL ES
  3.1 Mesa …)`, which is a **compatibility** adapter (see `docs/dogfood/m6.md`, item 6 of M1, and
  `examples/basic/main.js`). A core `requestAdapter` (what the P2 engine asks for, Conventions
  "WebGPU level (P2)") returns SwiftShader.
- Retrying the same commands cannot succeed (attempts 1..9 of card 4462 ran on the same host).

What was done by hand:
- Nothing was degraded. The lookdev page still requests a core adapter and never installs the
  compatibility wrapper of `examples/basic` (confirmed stack `webgpu_level`). No record was
  committed (records from a software adapter do not satisfy Q13).
- A model card cannot run an adapter probe on the client ("A model card never waits on a GPU
  job"). So the adapter list above comes from the capture output and the M6 record, not from a
  new probe.

What nomorechat must do instead (infrastructure, reported to the supervisor by the lead):
- Provide a GPU client whose Chrome exposes a **core** hardware WebGPU adapter. Examples: Chrome
  on Windows (D3D12 core), or a Linux client with a working Vulkan driver for the GPU instead of
  ANGLE/GL ES over WSL's D3D12. Then re-run `.nmc/commands.json` unchanged.
- Let a model card run a short adapter probe (seconds), or have the client report its core and
  compatibility adapters on connect. Then this kind of failure is found in one step instead of
  after 9 capture attempts.

Resolution (2026-10-23, lead answer):
- Since 17:20 the GPU clients are headless Windows Chrome on the RTX 3090 and register as vendor
  nvidia, architecture ampere, WebGPU level core, software false. No code or contract change:
  `webgpu_level` and the hardware check stay as they are, and `.nmc/commands.json` is re-run
  unchanged (attempt 10). If a capture still reports a software adapter, the adapter line it
  printed is reported to the supervisor.

## m07-base captures, attempt 10 (card 4486, core hardware client), 2026-10-23

What happened:
- `.nmc/commands.json` ran unchanged (`bash scripts/build-lookdev.sh`, then
  `node scripts/lookdev-capture.mjs --milestone m07`) and committed 7 records
  (`proofs/results/lookdev/m07-base--{agx,aces,exposure-up,msaa-on,msaa-off,vertex-colors,empty}.json`),
  all nonEmpty true, hardware true, isFallbackAdapter false, passes `prepass > forward > tonemap`,
  canvas 1280x720, judge null (no m07 variant is judged). First frame about 7 s (information only,
  timing caps suspended for P2).
- agx and msaa-on have the same captureSha256 (`6ca94f40…`): expected, both are the default
  settings (AgX, MSAA 4). The other five captures differ from each other.

What broke:
- **The adapter is not named in the records.** `vendor`, `architecture`, `device` and
  `description` are all empty strings in every record. `hardware` is true only because nothing
  matches the software regex and isFallbackAdapter is false, so the records cannot show that the
  RTX 3090 rendered them (Q9 asks that every browser record names the adapter). Cause not
  verified from a model card: the headless Windows Chrome probably returns an empty
  `GPUAdapterInfo`. The lead's statement (vendor nvidia, architecture ampere, core) comes from the
  client registration, not from the records.
- **The capture run modified a tracked file.** The committed root `LICENSE` has CRLF line ends;
  `scripts/build-package.sh` copies it over `packages/raa/LICENSE` (LF until then). So every run
  of build-package (and build-lookdev) dirties the worktree, and the programmatic card committed
  that rewrite with the records (`git diff --ignore-cr-at-eol 0adbe54^ 0adbe54` shows no content
  change).

What was done by hand: nothing. No record was edited, re-measured or substituted.

What nomorechat must do instead:
- Have the GPU client report the adapter info it registered with (vendor, architecture, level,
  software) in each job result, so a record can cite it when the page's `GPUAdapterInfo` is
  empty; or flag an empty adapter as a warning in the capture card.
- Show the programmatic card's `git status` (files other than the expected outputs) before it
  commits, so an unintended tracked-file change is caught by the card and not by a later task.
