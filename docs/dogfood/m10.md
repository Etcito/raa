# M10 dogfood: GPU client, sandbox and tooling

## Tuning inflatables against the judge (card 4748), 2026-10-24

Starting point: the first m10 capture (card 4747) had no judge run and no capture PNG reached
this card. Its records showed one real defect: `m10-materials--clearcoat-on.json` and
`--clearcoat-off.json` have the same `captureSha256` (01b3fb4e...), so the off variant was
a stand-in (Q15). Every value below was chosen on SwiftShader previews of the lookdev page
(m9's recipe: sandbox Chrome over a CDP pipe, a fresh tab per variant, 8 frames with 400 ms
pauses for the sky irradiance readback, 640x360 then 1280x720), placed beside ref-1.
Previews only, never records.

Values changed and why:
- `crates/raa-matfn/src/wgsl/inflatable.wgsl` and `candy.wgsl`: `o.clearcoat = 1.0` and
  `o.clearcoat_roughness` were hard-coded after `raa_default_output`, so the desc override
  `clearcoat: 0` never reached the BRDF. Both functions now keep the record's coat (desc
  `clearcoat`, `clearcoatRoughness`; record default 0). The previews of the pair now differ
  (glossy sky streaks over the pink gores with the coat, a satin ball without it).
- `raa.inflatable` base roughness 0.45 -> 0.24, `raa.candy` 0.35 -> 0.25: at 0.45 the balls
  read as matte (no highlight visible in the preview); at 0.3 a soft highlight appeared, at
  0.24 the seams and the sun side carry crisp white streaks closer to ref-1's wet-look
  plastic.
- Scene `COAT = { clearcoat: 1, clearcoatRoughness: 0.14 }` on every inflatable and candy
  material (`clearcoat-off` overrides the weight to 0). The old 0.04 coat made a sun glint
  far below a pixel at the capture cameras (GGX spot radius about R x 3 alpha = 1.5 mm on a
  0.32 m ball, pixels about 5 mm), so it never showed; at 0.14 it is a few pixels wide and
  still much sharper than the base lobe.
- Inflatables layout and camera: orbit [0, 0.5, 0] 4.2 m pitch 0.3 -> [-0.15, 0.55, 0.05]
  2.75 m yaw 0.08 pitch 0.12; balls, rings and hammer pulled into a tighter cluster and the
  hammer scaled 1.25 (`place` gained a uniform scale). The old view showed small objects on
  a floor filling half the frame.
- Inflatables floor: colour [0.2, 0.5, 0.95] roughness 0.3 -> [0.3, 0.65, 1] roughness 0.18
  (only this set; plush and user-fn keep the shared floor): ref-1's mats are a lighter cyan
  blue that mirrors the sky.
- Inflatable sets exposure 0 -> +0.35 EV (after the shared `daylight`): the render was darker
  and lower-key than ref-1's bright toy world. Yellow [1, 0.78, 0.1] -> [1, 0.84, 0.12]
  (it read mustard in the sky-lit shade).
- `clearcoat` close camera: [0, 0.6, 0] 2.2 m -> [-0.3, 0.62, 0.1] 1.75 m pitch 0.1, on the
  pink ball with the scaled hammer head behind.
- `inflatables` description: lists what the set really shows (hammer panels and caps, the
  four balls with their gores and stripes, a light blue floor).

Kept: the shared sun (35 deg, from the upper right and slightly behind, shadows to the
left as in ref-1), the `day` sky, AgX punchy, bloom defaults, seam depth 0.1/0.12.

Friction met:
- The capture PNGs of card 4747 did not reach this card, and that card ran without
  `--judge`, so there was no judge score or remark to tune against; the preview tool was
  rebuilt in /tmp a fourth time (m9 cards 4683, 4687, 4602).
- `crates/raa-matfn/README.md` still says both functions use "clear coat 1 (roughness
  0.04)" and the old base roughness; it is outside this task's file list. It should now say
  the coat comes from the desc (`clearcoat`, `clearcoatRoughness`), base roughness 0.24
  (inflatable) and 0.25 (candy). A desc without `clearcoat` gets no coat: a built-in that
  wants a default coat needs per-function defaults for the standard fields in `BUILTINS`.
- The jagged shadow terminator on the sun-facing balls in the previews comes from the m09
  shadow pass (outside this milestone's files); it may differ on hardware.

What nomorechat should do instead:
- Run the first capture of a judged variant with `--judge` and pass its PNGs and judge
  output to the tuning card; keep a one-variant software preview command in the tooling.

## m10-materials scene part 2 and capture handoff (card 4746), 2026-10-24

### Producer

What was done:
- `examples/lookdev/scenes/m10-materials.js` (part 1's variants and helpers kept): five new
  variants, 11 in total.
  - `plush` (judged against ref-1 and ref-2): the lookdev plush sphere in pastel pink and a
    penguin-like plush blob built from lib `uvSphere`s turned into ellipsoids (body, white
    belly patch, head, orange beak, rolled flippers, feet, glossy black eyes; one sub-mesh
    per part, merged), all in `raa.plush` with 16 mm fur (5 mm on beak and feet), under the
    m08 `day` sky on the glossy blue floor.
  - `fur-on` / `fur-off`: the same set from a close three-quarter camera on the penguin;
    `fur-off` disables `fur.shells` (Q15).
  - `user-fn`: `engine.addMaterialFunction('demo.checker', ...)`, an animated checker
    scrolling along u with `in.time`, colours and cell counts from `p0`..`p2`, on a sphere
    and a rounded box.
  - `mud-snow-tiles`: a 6 m grid in `raa.tiles` (0.25 m tiles), a flattened mud pool disc in
    `raa.mud` and a half-buried snow mound in `raa.snow`.
- `.nmc/commands.json` for the GPU card: `build-lookdev`, then `capture-m10` (`--milestone
  m10 --ref-prefix /refs/`, no `--judge`: this is the first capture; judging belongs to the
  tuning cards). Nothing was run on the GPU by this card.

Checks run in the sandbox:
- A stub-engine run of `build()` in node for all 11 variants: every method exists in the
  package types, mesh arrays have the right lengths, normals are unit, indices and sub-mesh
  ranges are valid, sub-mesh materials are live handles, material functions and parameter
  names and arities match `crates/raa-matfn/src/builtins.rs`, user params are `p0`..`p7`,
  disabled passes exist, and each `-on` has its `-off`.
- The `demo.checker` WGSL was registered with `MaterialFnRegistry::register_user` in a scratch
  crate under /tmp (path dependencies on raa-shader and raa-matfn, raa-lit's default slots and
  the ibl provider) and composed plus naga-validated for every pass kind at MSAA 1 and 4:
  it validates (a misspelt field is refused with `material.fn_invalid` and its line:col).
- A CPU z-buffer preview (python, flat Lambert, no fur) of the plush, fur, user-fn and
  ground cameras next to a crop of ref-2's penguin, to check framing and proportions.

Friction met:
- `raa.plush` declares `furLength` and `furDensity` as function params, and its WGSL comment
  says the mapping fills the record's `fur` from them, but `raa_matfn::map_desc` fills
  `record.fur` only from the desc fields `furLength`/`furDensity`/`furDroop`/`furShells`;
  the shell contributor reads the shell count from `record.fur[3]`. A plush material with
  only the params would draw no shells. The scene sets both (desc fields and params). The
  owner of raa-matfn should make the params feed the record or drop them.
- The task asks for "the same node stub check as part 1", but part 1 committed no script for
  it; the check was rewritten from the dogfood description into /tmp (not committed: the
  file list of this task has no place for it).
- Framing, fur length and colours were again chosen without a GPU render (a model card
  cannot run a GPU job, and SwiftShader in the sandbox fails the engine's `mapAsync`, see
  m9), so the first capture is the first real view of the fur.

What nomorechat should do instead:
- Keep a committed lookdev stub-check script (one place, e.g. under `tools/`) that every
  scene producer runs, instead of each card rewriting it.
- A software or GPU one-variant preview a model card may request (one PNG back), so fur and
  framing can be tuned before the programmatic card.
- A shared "validate this user WGSL" command (the registry check above) available without a
  scratch crate.
