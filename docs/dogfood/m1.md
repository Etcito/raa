# M1 dogfood: GPU client, sandbox and tooling

Capture of `m1-boot` (card 3115) on 2026-10-17. Recaptured on the third attempt, after
the toolchain fix of item 1 changed which rustc builds the wasm. Commands run:

```
bash scripts/build-web.sh demos/m1-boot
/root/nmc/engines/bin/node scripts/gpu-capture.mjs m1-boot
/root/nmc/engines/bin/node proofs/m1-boot.mjs
cargo test -p raa-core --test gpu_readback -- --nocapture
```

## Result

- `proofs/results/m1-boot.json` was written by `scripts/gpu-capture.mjs` from the GPU
  client's op result (not edited by hand): nonEmpty true, firstFrameMs 105,
  cpuMsMedian 0.20 ms / cpuMsP95 0.30 ms per frame (1 triangle, 60 warm-up + 300
  frames), resize cycle ok, wasm 167847 B raw / 68097 B gzip.
- Browser adapter: "SwiftShader Device (Subzero)", `isFallbackAdapter` true. This is a
  **software** adapter (CPU rasteriser), not the hardware GPU. `hardware` is false.
- `proofs/captures/m1-boot.png` (gitignored, for R1 review) shows one solid orange
  triangle centred on the dark clear colour, without garbage, stripes or tearing.
- Native readback in the sandbox: `cargo test -p raa-core --test gpu_readback`
  **PASS**, not SKIP. The sandbox exposes a native adapter: wgpu reports
  `D3D12 (NVIDIA GeForce RTX 3090)` on the Gl backend (Mesa over WSL D3D12), which is
  **hardware**; pixel 0 read back as [13, 15, 20, 255] (CLEAR_COLOR x 255).
  No Chrome was launched in the sandbox. Browser WebGPU went only through the GPU client.
- Proof: all four CHECK lines PASS and the script exits 0 (browser-run, check-sh,
  wasm-size, serve), in the bare sandbox env (no RUSTC, empty NO_PROXY). On the second
  attempt it passed only with hand-set env (RUSTC, PATH, NO_PROXY), and nomorechat's
  own proof run then failed at `cargo test`. The third attempt moved those workarounds
  into the repository (items 1, 3 and 7).

## Frictions

1. **Managed rustc has no wasm32 target.** `~/.cargo/config.toml` (kong-managed) sets
   `build.rustc` to the kong 1.99.1 toolchain, which ships only the x86_64 std. So
   `scripts/build-web.sh` failed with `E0463 can't find crate for core`.
   Done by hand on attempt 2: `RUSTC=/root/.rustup/toolchains/stable-x86_64-unknown-linux-gnu/bin/rustc`
   (1.96.0, which has the wasm32-unknown-unknown std). That fixed only the shell of that
   attempt. In nomorechat's proof run, `cargo test` still failed: rustdoc from PATH
   (1.96.0) rejected deps built by the kong rustc (`E0514` in the raa-core doctests).
   Fixed on attempt 3: `scripts/check.sh` and `scripts/build-web.sh` export
   `RUSTC=$(command -v rustc)` when RUSTC is unset. That rustc is the one whose rustfmt,
   clippy and wasm32 std check.sh verifies, so rustc, rustdoc, clippy-driver and the
   wasm std all come from one toolchain. An explicit RUSTC still wins. Plain `cargo check`
   (nomorechat's check) keeps using the kong rustc and passes.
   nomorechat must: ship `wasm32-unknown-unknown` in the managed toolchain, or not
   override `build.rustc` for projects that declare a wasm target.
2. **wasm-bindgen CLI missing.** Conventions require `wasm-bindgen` 0.2.129 on PATH. It
   was not there. Done by hand: downloaded the official
   `wasm-bindgen-0.2.129-x86_64-unknown-linux-musl` release into `/tmp/nmc-tools`
   (outside the repo) and prepended it to PATH.
   nomorechat must: provide the pinned CLI version with the toolchain.
3. **rustfmt and clippy: first missing, then mismatched with the managed rustc.** On
   the first attempt `scripts/check.sh` stopped with `required toolchain component(s)
   missing: rustfmt clippy` (no rustup on PATH, read-only toolchain). On the second
   attempt both were present (rustfmt 1.9.0-stable, clippy 0.1.96, from the rustup 1.96.0
   toolchain), which showed three things:
   - code written before rustfmt existed was not formatted. Fixed with `cargo fmt --all`
     (whitespace only) in crates/raa-core, crates/raa-web and demos/m1-boot/src/lib.rs;
   - two clippy lints: `int_plus_one` in crates/raa-core/src/graph.rs and
     `manual_is_multiple_of` in crates/raa-web/src/stats.rs. Fixed with clippy's own
     suggestion; behaviour is unchanged;
   - `cargo clippy` fails with `E0514 found crate wgpu compiled by an incompatible
     version of rustc`: dependencies are built by the kong `build.rustc` (1.99.1), while
     clippy-driver is 1.96.0. Fixed on attempt 3 by the RUSTC export of item 1.
   nomorechat must: ship clippy, rustfmt and the wasm32 std for the SAME rustc that
   `build.rustc` points at, or not override `build.rustc`.
4. **GPU client protocol undocumented.** `docs/gpu-client.md` was not reachable next to
   `$NMC_GPU_CLIENT`, so the page manifest was guessed at M1 and publish refused it
   (`nmc.gpu.json requires a page string`, then `ops must be operation names`, then
   `Operation not declared by this revision`, then `Render operation unavailable`).
   Learned by probing with throw-away pages:
   - `nmc.gpu.json` needs `"page": "<entry html>"` and `"ops": [<names>]`;
   - the client calls `window.nmcGpu.ops[<cli op>](input, {})`. The CLI op is `render`,
     and `input` is the whole input file;
   - the op must resolve to `{ json, files: [{ name, base64 }] }`. `json` lands under
     `result` in `<out>/result.json`, and each file is written to `<out>/<name>`;
   - the client takes no screenshot itself. The page must return the PNG.
   Fixed in `demos/m1-boot/web/nmc.gpu.json`, `demos/m1-boot/gpu-input.json`,
   `demos/m1-boot/web/main.js` and `web/common/nmc-gpu.js` (a `render` op that wraps
   `run(input.args)` and adds the canvas PNG).
   nomorechat must: put the protocol doc next to the client, or print it from
   `node "$NMC_GPU_CLIENT" --help`.
5. **requestAnimationFrame starves in the client's headless Chrome.** rAF fired once
   in about 3 s, so the measured run never finished. The job failed only after
   `Render page timed out (595 s)`, with no earlier progress or console output.
   Fixed in `web/common/run-loop.js`: `nextFrame()` falls back to a 34 ms timer when rAF
   is late. The page's idle loop uses it too, so frame 0 (firstFrameMs) does not wait
   for rAF. Frame pacing in the client is therefore timer-driven.
   nomorechat must: run the page with a working begin-frame source (or document that
   rAF is throttled), and return page console errors and a timeout reason much sooner.
6. **Hardware adapter only at compatibility feature level.** In the client's Chrome,
   `requestAdapter()` with no options or with `powerPreference` returns SwiftShader
   (fallback). Only `{ featureLevel: 'compatibility' }` returns
   `ANGLE (Microsoft Corporation, D3D12 (NVIDIA GeForce RTX 3090), OpenGL ES 3.1 Mesa
   26.0.3-1ubuntu1)` with `isFallbackAdapter` false. raa-core requests a core adapter
   through wgpu, so M1 runs on software. This is fine for M1 (no speed threshold). M2's
   CPU criterion needs `hardware: true`.
   Follow-up for the lead: either raa-core requests a compatibility-level adapter on
   the web, or nomorechat exposes core-level WebGPU on the GPU in the client Chrome.
   Also, on the web raa-core's adapter summary puts the name in `device` and leaves
   vendor/architecture/description empty (information only; labelling is still correct).
7. **Node proxies loopback.** The sandbox sets `NODE_USE_ENV_PROXY=1` with empty
   `NO_PROXY`. Node's `fetch('http://127.0.0.1:<port>/')` therefore goes through the
   sandbox proxy, and the proof's `serve` check fails with `fetch failed`. Fixed on
   attempt 3: `proofs/m1-boot.mjs` fetches with `node:http` and its own `Agent`, which
   bypasses the env proxy (all 200, wasm `application/wasm`).
   nomorechat must: put `127.0.0.1,localhost` in `NO_PROXY`/`no_proxy`.
8. **Env-value redaction makes capture logs unreadable.** `scripts/gpu-capture.mjs`
   redacts every non-empty env value, and the sandbox env holds values like `1` and
   `0`. So its log prints `m[REDACTED]-boot` and mangled numbers (the written JSON is
   not affected). nomorechat could mark which env values are secret (only
   `NMC_GPU_TOKEN`), so tools can redact precisely.
9. **The managed proof run used a different env from the task shell.** The task shell
   had RUSTC set and a wasm-bindgen in `~/.cargo/bin`. The orchestrator's proof run did
   not have that RUSTC, so a proof that passed for the task failed for nomorechat.
   nomorechat must: run the task and its checks in the same env, or print the checks'
   env differences (variable names only) together with the failure.
